# mono-api-agent

RAG-агент по офіційних OpenAPI-специфікаціях monobank: відповідає на питання
про інтеграцію, спираючись виключно на документацію, і вміє сходити в живий API.

Побудований на тому, що monobank публікує сам — [AI Skills для агентів](https://monobank.ua/api-docs/acquiring/dev/ai-tools/docs--ai-skills)
прямо передбачають власні RAG-системи поверх їхньої документації.

## Що всередині

| Компонент | Рішення |
|---|---|
| Корпус | 25 ендпоїнтів + 45 схем із двох офіційних специфікацій (`personal`, `acquiring`) |
| Ембединги | локальні, `Xenova/multilingual-e5-small` через transformers.js — без ключа й без оплати |
| Пошук | гібридний: косинусна близькість + лексичний збіг |
| Оркестрація | LangGraph зі self-check і циклом уточнення |
| Живі дані | публічний `/bank/currency` (єдиний метод без токена) |
| LLM | будь-який OpenAI-сумісний: Groq, OpenRouter, Anthropic, OpenAI |
| Спостережуваність | час, виклики моделі й токени по кожному вузлу графа |

## Граф

```
           ┌─────────┐
  START ──▶│  route  │── питання про курс? ──▶ ┌───────────┐
           └─────────┘                         │ fetchLive │
                │ ні                           └─────┬─────┘
                ▼                                    │
           ┌──────────┐◀───────────────────────────── ┘
           │ retrieve │◀──── уточнений запит ──┐
           └────┬─────┘                        │
                ▼                              │
           ┌──────────┐     ┌────────┐  контексту    │
           │ generate │────▶│ verify │── не вистачає ─┘
           └──────────┘     └───┬────┘
                                │ достатньо
                                ▼
                               END
```

Цикл існує тому, що перший пошук часто промахується на питаннях, сформульованих
не термінами документації — «як брати гроші з картки» замість «invoice create».
Вузол `verify` має право переформулювати запит термінами OpenAPI і сходити в
пошук ще раз, з ширшим `k`. Не більше двох проходів, інакше на поганому питанні
граф крутився б вічно.

## Запуск

```bash
npm install
npm run ingest                  # завантажує специфікації, рахує ембединги (~1 хв)
cp .env.example .env            # і вписати один ключ

npm run ask -- "як створити рахунок і перевірити, чи його оплатили?" --trace
npm run ask -- "який зараз курс євро?"
```

Без ключа теж працює — дивитись сам пошук або хід графа:

```bash
npm run search -- "як перевірити підпис вебхука"
MONO_AGENT_FAKE_LLM=1 npm run ask -- "будь-яке питання" --trace
```

## Чому пошук саме такий

**Ембединг рахується не по всьому чанку.** Перша версія індексувала повний текст
ендпоїнта, і пошук промахувався: опис методу займає два рядки, а розкрита схема —
сорок, тож вектор описував переважно назви полів. На питання «як створити рахунок»
`invoice/create` не потрапляв навіть у топ-3. Тепер у ембединг іде призначення
методу + імена полів верхнього рівня, а повний текст віддається моделі як контекст.

**Лексичний доданок.** Чисто векторний пошук на цьому корпусі давав дуже щільні
оцінки — усе в межах 0.82–0.87. Модель бачить, що всі 70 чанків про одне платіжне
API, і погано їх розрізняє. Точний збіг слова `invoice`, `statement`, `webhook` —
сильний сигнал, який вектор недооцінює, тож він додається окремо з вагою 0.25.

**Бюджет контексту.** Чанк із повністю розкритими схемами буває під 10 000 символів;
п'ять таких давали 46 000 — дорого й не влазить у менші вікна. Кожен чанк і загальна
сума обрізаються, бюджет витрачається згори вниз.

## Скільки коштує прохід

`--trace` показує не лише маршрут, а й ціну:

```
— вартість проходу:
всього 662 мс · викликів моделі 0 · токенів 0

  route           0 мс    0%
  retrieve      657 мс   99%
  generate        1 мс    0%
  verify          0 мс    0%
  retrieve        4 мс    1%
```

Це не прикраса. Вузол `verify` майже подвоює кількість викликів моделі, і без
поділу токенів по вузлах неможливо вирішити, чи варта самоперевірка своїх грошей.
Заміри одразу показали й інше: перший `retrieve` коштує 657 мс, повторний — 4 мс.
Різниця — не пошук, а холодний старт локальної моделі ембедингів.

## Що вимірювалось

Після переходу на сфокусований ембединг + лексичний доданок:

| Питання | Топ-1 |
|---|---|
| як створити рахунок і перевірити оплату | `POST /api/merchant/invoice/create` |
| як перевірити підпис вебхука | `GET /api/merchant/pubkey` |
| виписка по картці за минулий місяць | `GET /personal/statement/{account}/{from}/{to}` |
| як скасувати платіж і повернути гроші | `POST /api/merchant/invoice/cancel` |
| регулярні списання з картки | `POST /api/merchant/wallet/payment` |

## Відомі обмеження

- Питання про **рейт-ліміти** знаходяться погано: ліміти згадані всередині описів
  окремих методів, а не винесені в окрему сутність, тож пошуку немає за що
  зачепитись. Тут потрібен окремий чанк із загальних правил API.
- Корпус — **лише специфікації**. Гайди, приклади коду й опис ECDSA-верифікації
  вебхуків живуть в іншому місці документації і поки не індексуються.
- Крос-мовність не ідеальна: документація українською, і питання російською
  ранжуються трохи гірше за україномовні.
- `/bank/currency` у monobank лімітований одним запитом на 60 секунд — відповідь
  кешується, тому курс може бути до хвилини несвіжим.
